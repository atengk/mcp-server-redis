# 领域文档规范 (Domain Docs)

工程技能在探索、分析及修改代码库时读取与消费本项目领域文档的标准指引。

---

## 探索代码库前的优先阅读清单

1. 仓库根目录下的 **`CONTEXT.md`**：核心领域术语表与统一语言定义；
2. 根目录下的 **`CONTEXT-MAP.md`**（若存在多领域上下文架构）：该文件将索引各个子领域的 `CONTEXT.md`，请按需调阅与当前任务强相关的上下文文档；
3. **`docs/adr/`**：架构决策记录（Architecture Decision Records）。在着手修改特定功能前，需查阅影响该区域的历史技术决策。

> **静默执行原则**：若上述文档或目录尚未创建，**请静默继续执行**，严禁主动报错或阻断流程，亦无需主动建议用户预先创建。`/domain-modeling` 技能（可通过 `/grill-with-docs` 或 `/improve-codebase-architecture` 触发）会在实际确立概念术语或架构决策时按需初始化创建。

## 目录结构布局

单上下文代码库布局（本项目采用）：

```
/
├── CONTEXT.md               ← 核心领域术语表与统一语言 (Ubiquitous Language)
├── docs/adr/                ← 系统级架构决策记录 (ADR)
│   ├── 0001-fastmcp-architecture.md
│   └── 0002-read-only-guard-pipeline.md
├── docs/agents/             ← 智能体工程技能配置与交互规范
└── src/                     ← 核心业务源码
```

## 术语表与统一语言约束

在生成的产物（包括 Issue 标题、重构方案、分析假设、测试用例命名等）中提及业务或技术领域概念时，必须严格采用 `CONTEXT.md` 中已定义的标准术语，严禁随意引入术语表中已明确规避的同义词或歧义词汇。

若所需概念尚未收录在术语表中，这通常意味着两个信号：
1. **创造了非标准词汇**：可能正在发明项目当前未采用的概念表述（需重新审视收敛）；
2. **存在概念定义缺口**：发现了真实的业务/技术定义空白（记录并在后续通过 `/domain-modeling` 补充归纳）。

---

## 架构决策记录 (ADR) 冲突警示

若提出的方案或实现与现有 ADR 决策冲突，必须显式在输出中指出并说明理由，严禁静默覆盖已有决策：

> _与 ADR-0002（只读安全守卫流水线）存在冲突——建议重新审视该决策，原因为：..._
