# ADR-0007: Redis Cluster 分片集群自适应驱动、单一数据库约束与跨槽安全防御

- **状态**: 已采纳 (Accepted)
- **决策日期**: 2026-10-04

---

## 背景与问题陈述

生产环境中的 Redis 部署形态涵盖单机、主从哨兵以及基于哈希槽 (Hash Slot 0~16383) 的分布式分片集群 (Redis Cluster)。在向 Redis Cluster 演进时，MCP 服务端面临以下严峻的架构约束与运行风险：
1. **多节点拓扑与驱动差异**：标准单机 `redis.asyncio.Redis` 无法处理集群节点的 `MOVED` / `ASK` 重定向与槽位路由，必须初始化专用的 `redis.asyncio.cluster.RedisCluster` 驱动并维护多节点拓扑连接；
2. **集群不支持多数据库 (Only DB 0)**：原生 Redis Cluster 规范彻底废弃了多逻辑库特性，仅支持 `0` 号数据库。若客户端仍按单机惯性传入 `db=1~15` 或 URL 携带 `/<db>` 路径，驱动会抛出 `ResponseError: SELECT is not allowed in cluster mode` 直接引发服务崩溃；
3. **跨槽多键操作崩溃 (CROSSSLOT Error)**：单机支持以变长参数批处理多个键（如 `DEL key1 key2`、Pipeline 批量执行等）。但在分片集群中，若传入的多个键分散在不同的哈希槽（且未指定 Hash Tag `{...}`），Redis 会直接返回 `CROSSSLOT Keys in request don't hash to the same slot` 阻断执行；
4. **全库检索单节点局限**：单机 `SCAN` 游标仅绑定单个实例，在集群中无法通过单游标扫描全部分片节点的键空间。

---

## 决策内容

为实现对单机与集群透明自适应且绝对安全的高可用交互，确立以下架构决议：

1. **协议层自适应识别与连接串物理净化**：
   - 自动识别 `redis-cluster://` 与 `rediss-cluster://` 协议头，内部自适应归一化为标准协议并标记 `is_cluster=True`；
   - 亦支持通过环境变量 `MCP_REDIS_CLUSTER=true` 或多实例配置 `cluster: true` 显式激活；
   - **连接串净空防御**：在初始化集群驱动前，底层自动剥除 URL 尾部的 `/<db>` 路径，杜绝非标准路径引发底层驱动解析与校验崩溃。

2. **单一数据库 (DB 0) 强制防御契约**：
   - 严禁在集群模式下向底层发起任何 `SELECT` 指令；
   - 若上层工具或请求传入非 0 的 `db` 参数，注册中心执行深度防御：自动记录审计告警并重置绑定至 `db=0`，绝不因参数误传而使大模型任务中断崩溃。

3. **跨槽 (Cross-Slot) 安全防御与并发提速**：
   - **物理删除 (`redis_delete_keys`)**：检测到目标为 `RedisCluster` 客户端或捕获到 `CROSSSLOT` 跨槽异常时，自动将批处理安全收敛为基于 `asyncio.gather` 的并发单键独立删除；在彻底阻断跨槽崩溃的同时，避免串行网络 N+1 延迟；
   - **探活安全降级**：未确认删除前的 Pipeline 批量探活阶段，若遭遇集群网络或代理异常，自动降级为并发逐键存在性探测。

4. **集群全节点聚合遍历扫描 (`client.scan_iter`)**：
   - 在键检索工具 `redis_scan_keys` 中针对集群模式分流，自适应调用 `RedisCluster.scan_iter`；
   - 驱动内部自动遍历集群全部 Master 节点，在服务层聚合收集并受 `effective_limit`（默认 50，硬上限 200）安全截断保护，返回格式与单机保持一致。

5. **网络超时防护与故障转移自动重试**：
   - 默认注入生产级 `socket_connect_timeout=3.0s` 与 `socket_timeout=5.0s` 兜底保护，并支持通过环境变量自定义配置；
   - 集群驱动显式开启 `cluster_error_retry_attempts=3` 与 `retry_on_timeout=True`，从容应对节点故障转移与拓扑抖动。

## 影响与权衡

- **积极收益**：
  - **零侵入透明纳管**：上层工具统一透传 `connection` 与 `db`，底层自动适配单机或分片集群，无需针对集群定制两套工具契约；
  - **杜绝跨槽崩溃风险**：通过并发单键执行与异常降级双重保障，彻底终结了分布式 Redis 环境中偶发性的跨槽致命报错；
  - **网络与超时兜底完善**：大模型会话彻底免除底层连接永久挂起的风险。
- **潜在代价与权衡**：
  - 对海量跨槽键进行物理删除时，网络请求数等于目标键数量（由 `asyncio.gather` 并发弥补时延开销），但在 MCP 单次请求受控的键数范围内（通常 $\le 50$ 条），性能表现与系统安全性达到最佳平衡。
