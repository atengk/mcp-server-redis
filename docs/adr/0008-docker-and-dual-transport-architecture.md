# ADR-0008: 生产级容器化构建策略与常驻 SSE 双模传输网关架构

- **状态**: 已采纳 (Accepted)
- **决策日期**: 2026-10-04

---

## 背景与问题陈述

随着 `atengk-mcp-server-redis` 迈向生产级交付，单纯依赖本地宿主机运行（Stdio 管道）已无法满足企业级部署与远程大模型协作的需求，面临以下架构挑战：
1. **多环境部署摩擦**：传统 Python 应用依赖宿主机 Python 运行环境与依赖包管理，环境差异易导致不可预测的兼容性与部署故障；
2. **构建时延与镜像膨胀**：传统 `pip install` 构建耗时长，若将全量编译工具链打包入镜像，将导致镜像体积飙升（通常 $> 500\text{MB}$），消耗高额带宽与存储成本；
3. **容器安全基线**：以容器默认的 `root` 用户运行进程存在严重的容器逃逸与提权安全风险，不符合生产安全审计合规要求；
4. **远程服务化接入需求**：在团队协作、私有化云平台或 Kubernetes 微服务场景下，客户端无法直接通过本地命令行启动子进程管道，亟需标准 HTTP Server-Sent Events (SSE) 网络网关提供稳定常驻服务；
5. **宿主机网络互通**：容器在连接宿主机已有的单机或集群 Redis 服务时，需要具备跨平台（Linux、macOS、Windows）平滑解析宿主机网络的能力。

---

## 决策内容

经过工程推演与基线评测，确立以下生产级容器化架构与构建策略：

1. **基于 `uv` 的极速多阶段精简构建 (Multi-Stage Build)**：
   - **构建阶段 (Builder)**：从 `ghcr.io/astral-sh/uv:latest` 提取预编译高性能 `uv` 二进制，基于 `python:3.11-slim` 先行挂载缓存编译项目运行时依赖，最大化复用 Docker 镜像缓存层；
   - **生产运行阶段 (Runtime)**：以纯净的 `python:3.11-slim` 作为底层底座，仅复制虚拟环境 `/app/.venv` 与业务代码，剔除编译器与包构建工具链，确保产出镜像体积严格收敛在 $150\text{MB}$ 以内。

2. **专有非 Root 用户安全基线 (Non-Root User)**：
   - 显式在镜像内部建立专有系统账户与组：`appuser` (UID: `10001`, GID: `10001`)；
   - 将工作目录 `/app` 与虚拟环境的所有权严格赋予 `appuser`，运行阶段通过 `USER appuser` 执行权限下沉，满足企业级安全准入与最小特权原则 (Least Privilege)。

3. **双模传输网关契约与开箱即用常驻配置**：
   - **默认入口**：配置 `ENTRYPOINT ["atengk-mcp-server-redis"]`，保证容器兼具“微服务常驻组件”与“命令行 CLI”双重形态；
   - **默认启动模式**：`CMD ["--transport", "sse", "--host", "0.0.0.0", "--port", "8000"]`，默认以 HTTP SSE 网关模式在 `0.0.0.0:8000` 常驻运行；若用户需要通过 Docker 运行 stdio 管道，仅需在运行时追加 `--transport stdio` 即可平滑覆盖。

4. **开箱即用单服务编排 (`docker-compose.yml`)**：
   - **官方 GHCR 镜像优先**：默认直接消费 GitHub Actions CI/CD 自动化构建的多架构官方镜像 `ghcr.io/atengk/mcp-server-redis:latest`，单文件拷贝到任何环境即可一键拉取启动，无需克隆源码；
   - **开发源码构建插槽**：将 `build: { context: ., dockerfile: Dockerfile }` 作为注释块保留，兼顾开箱即用与本地源码二次开发调试需求；
   - **动态参数替换与环境协同**：环境变量采用 `${VAR:-default}` 标准插值语法，与 `.env` 配置文件（基于 `.env.example` 派生）形成无缝联动，并在缺省时依赖保底默认值平滑运行；
   - **跨平台网络互通**：注入 `extra_hosts: ["host.docker.internal:host-gateway"]`，无缝支持容器直连 Linux/macOS/Windows 宿主机上的外部 Redis 服务。

5. **严格的资产隔离与防护规则 (`.dockerignore`)**：
   - 物理阻断 `.git`、`.venv`、`tests/`、开发排查脚本 `scratch/`、日志文件与各类调试缓存打包进镜像，保障镜像的轻量与数据资产的绝对安全。

---

## 影响与权衡

- **积极收益**：
  - **秒级启动与极小体积**：利用 `uv` 缓存优化与多阶段构建，冷拉取与部署效率显著提高，镜像体积极致收敛；
  - **生产安全合规**：非 root 运行与零敏感资产泄露，全面符合企业容器安全审计规范；
  - **网络接入与双模兼容**：不仅支持本地 stdio 容器调用，更能作为微服务直接纳入远程 MCP 客户端网络生态。
- **潜在代价与权衡**：
  - 在 Linux 生产环境下使用 `host.docker.internal` 时需依赖 Docker Engine 20.10+ 的 `host-gateway` 特性，已在 compose 配置中标准内建。
